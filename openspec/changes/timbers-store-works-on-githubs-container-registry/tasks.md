# Tasks

Every command runs from the place's root, inside `devenv shell`.
Commit by pathspec, Conventional Commits scoped to the part of the
tree, citing clauses by number and rules by id. Submit nothing: Flume
submits the place once its last stage delivers. The headings are for
reading; each task's check is its own. Read
`crates/timber/src/profiles/store/registry/client.rs`,
`crates/timber/tests/registry_ecr.rs` and
`crates/timber/tests/registry/mod.rs` before starting. No seam trait,
shared type, OCI form or binding changes; a task that cannot be done
without one stops short with `flume needs`.

## 1. A write's token

- [x] 1.1 In `crates/timber/src/profiles/store/registry/client.rs`, give `Client::authorize` the request's method and the repository `send` was given (design D2). For a `Bearer` challenge, a write, any method but `GET` and `HEAD`, asks the realm for `repository:<repository>:pull,push`. A read asks the challenge's scope as before. `service` stays the challenge's, and the token is held under the repository as before. Say so in the module comment. Add the unit test `a_write_asks_to_pull_and_push_its_repository` to the module's tests, over the stub as `a_token_for_one_repository_is_kept_beside_anothers` builds it. The stub answers every request with no bearer with `scope="repository:one:pull"`, keeps each token request's query, and answers `200` to a request with the token. Assert that a `PUT` of `/v2/one/manifests/x` asks the realm for `scope=repository%3Aone%3Apull%2Cpush` and is answered `200`, and that a `GET` from a fresh client asks for `scope=repository%3Aone%3Apull`. Verify with `devenv shell -- cargo test -p timber --lib profiles::store::registry::client::tests`, where the new test and the module's existing tests pass.
