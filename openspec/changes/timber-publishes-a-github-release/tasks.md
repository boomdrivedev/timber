## 3. The GitHub release target

- [ ] 3.1 Declare `github_release` in `profiles/target/mod.rs`, and add `crates/timber/src/profiles/target/github_release/mod.rs` holding `PROFILE = "github_release"`, and `github_release/table.rs` reading `github_release = { credential, assets }` as the github-release-target spec and design D3 give it. Give it unit tests for each key's forms, an empty `assets`, an asset with a space, one beginning or ending with `.`, a repeated asset, a `token` key, and settings that are no table. Verify with `devenv shell -- cargo test -p timber --lib profiles::target::github_release::table`.
- [ ] 3.2 Add to `github_release/mod.rs` the `GithubRelease` target over a store binding of its own, the checkout's repository, the credentials, and a backend behind a trait private to the profile, whose operations are `tag`, `release`, `create`, `upload`, `publish` and `latest`, each handed the repository and the token (design D1). Add `github_release/scripted.rs`, a `Scripted` backend holding tags, releases with their assets and digests, and the latest release in memory. It answers each operation as a test sets, fails any operation with words a test gives or every operation handed a given token, and records each operation asked in order with its token. Bind `GithubRelease` in the family's `bound` under `github_release`, and say so in `bound`'s comment. In `bindings/tests.rs`, make the profiles an apply binds `["clan", "dash0", "github_release", "nix_cache"]`. Verify with `devenv shell -- cargo test -p timber --lib bindings::tests::an_apply_binds_every_target_built_through_a_store_it_never_makes`.
- [ ] 3.3 Read the token at the moment of use (github-release-target spec, "The credential is the host's, read at the moment of use"; design D4). Look up the table's `credential` in the host's credentials and read the file it names, trimming trailing whitespace. A name the host's file lacks is unreadable naming it and the bindings file. A file that can't be read is unreadable naming the credential and the path, with the operating system's words. A file of whitespace alone is unreadable naming the credential. Add `github_release/tests.rs` with a submodule `credential`, over `Scripted`, covering each of those with no operation asked, a trailing newline trimmed from the token the backend is handed, and the token in no answer's words. Verify with `devenv shell -- cargo test -p timber --lib profiles::target::github_release::tests::credential`.
- [ ] 3.4 Add `github_release/gh.rs`, the backend that runs `gh` through the run module's `Tool` (github-release-target spec, "The token reaches each run of `gh` alone" and "No run of `gh` reads the host's own settings"; design D4, D6, D9):

  - Every `GH_*` and `GITHUB_*` variable is removed. `GH_CONFIG_DIR`, `GH_TOKEN`, `GH_PROMPT_DISABLED` and `GH_NO_UPDATE_NOTIFIER` are set for the run alone.
  - The arguments are design D6's and D9's, with `--repo github.com/<owner>/<name>` and `--hostname github.com`.
  - `release not found` from `gh release view`, and `gh: Not Found (HTTP 404)` from `gh api`, answer none. Any other failure is unreadable with `gh`'s stderr verbatim.
  - A tag object is peeled to its commit with a second `gh api`. An asset with no digest reads as one holding none.
  - Test it with a stand-in `gh` shell script, as the Dash0 target's tests stand in for `dash0`. The script records its arguments, its environment and the contents of its `GH_CONFIG_DIR`, and prints what a test sets with the exit a test sets. Cover each operation's arguments; `GITHUB_TOKEN`, `GH_HOST`, `GH_REPO` and `GH_CONFIG_DIR` set in timber's environment and absent from the run's, or replaced; the folder empty and not the host's; `GH_TOKEN` the token, and the token in no argument; both not-found wordings; a lightweight tag and a tag object; and another failure's words carried.
  - Verify with `devenv shell -- cargo test -p timber --lib profiles::target::github_release::gh`.
