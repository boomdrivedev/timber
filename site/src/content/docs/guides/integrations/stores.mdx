A store holds bytes by digest, never alters them, and answers the same
bytes for the same digest for as long as it holds them; one that cannot
is not a store (73). Exactly one store is written by a publish (92).

## The contract

The seam is eight operations (66 to 72, 138). **put-bytes** takes bytes and
their digest and says whether the store held them already; the same
bytes put twice are held once. **put-artifact** takes an artifact's
metadata and the digests of its bytes and answers the artifact's digest,
which the store names it by thereafter. **attach** puts an attestation
beside a digest, where **claims-of** reads every attestation attached to
that digest, as attached, or says the digest is not held. **name** moves
a name to a digest only from the digest it is expected to be at, and
otherwise refuses, naming the digest it is at; a name moved from nothing
is a name made. **resolve** answers the digest a name names, or that it
names nothing. **read** answers a digest's bytes, or that the digest is
not held. **versions**, given an ecosystem and a name, answers every
version the store names that name at, the empty list where it names
none, and unreadable only where the listing cannot be read, never an
empty list for a read that failed (138).

## Names

A publish names each artifact of a version by its ecosystem, its name
and its version, `artifact/<ecosystem>/<name>@<version>`, at the
version's index: after the index is put and the publisher's layout
policy attached to it, and before the version's own name, so every
version the store names can be found by what a lockfile pins, and a
consumer resolving the name finds on the index the claims a layout
needs (113, 138). The name is built from the artifact alone and names no
host, store, component, tag prefix or repository, so it is the same in
every store (49). It is made from nothing and never moved: a publish
reads every artifact's name first, leaves one already at this index,
and refuses the version, naming the name and both indexes, where one is
at another (70). A second publish of a revision makes any name the
store lacks at its index, so a version published before artifacts were
named gets its names the next time it is published.

A version's own name is its tag, `v1.2.0`, where the repository declares
no component, and `<component>:<tag>`, `lib:lib-v1.2.0`, where it
declares one, so every store can tell whose version it is (125, C.1).
The index names the revision it was published from and the publishing
repository by the owner and name of its landed branch's remote, as the
remote's address is written, in the annotations
`org.opencontainers.image.revision` and
`io.github.agentplot.timber.repository`; an index whose repository has
no such remote names none, and one put before indexes named them keeps
its bytes and its digest (13).

A registry holds the store under one root the host names, such as
`<account>.dkr.ecr.<region>.amazonaws.com/timber` or
`localhost:5000/timber`, and the store never makes a repository. Every
name of the store is a tag of a repository under the root, in three
spaces a credential, or a package's visibility, can be scoped to apart
(C.1 as amended at `boomdrivedev/blueprints` f412008, 135; ADR 0023,
record 0040):

- **The repository's own**, `<root>/<owner>/<name>`, for the repository
  the store is bound for, the owner and name its landing's remote gives,
  lowercased (114, 138). It holds the tags of a repository that declares
  no component, and every blob, artifact, index and attestation a
  publish writes before any name reaches it. A store bound for no
  repository, as a checkout with no remote's is, answers every write
  and every name of these spaces absent naming the landing's remote, and
  reads the artifact space as any store does.
- **A declared component's repository**, `<root>/<owner>/<name>/<component>`:
  its versions' tags, `lib-v1.2.0` for `lib:lib-v1.2.0`, and its
  channels' names, `beta` for `channel/lib/beta`, are its tags, and each
  of its indexes is held there from the publish that puts it.
- **Cache entries**, `<root>/<owner>/<name>/cache/<build>`, one per build
  profile: the build identity is the tag. A push puts its bytes there
  and asks nothing of the repository's own.
- **An artifact's name**, `<root>/artifact/<ecosystem>/<name>`, one
  space for the whole store and under no repository's own: the version
  is its tag, so a name's versions are its tag list, its index's
  referrers tag left out. A consumer finds a pin by ecosystem, name and
  version alone, and reads the version's claims beside its index there.

A name's repository holds what its tag reaches and the claims beside
it: before a tag is put, the index or manifest it names, everything that
names, and timber's attestations on each are held there, mounted from
the repository the store found them in, or uploaded under their own
digests where a registry declines the mount. A digest is read where its
name was resolved: the store keeps, for its life alone, the repository
each name it resolved or made is in and the digests a manifest read
there names, and a read, claims-of, attach or name asks those first,
then the repository's own, then the cache repository. A claim is
written into each repository holding its subject: the repository's own,
each repository the subject was reached in, and, for an index, its
component's repository and each of its artifacts' names' repositories,
each where the attestation is missing.

A repository renamed or moved to another owner keeps one history in the
store (C.1 as amended at `boomdrivedev/blueprints` e8700c8; records
0040, 0041 and 0042). Its record of claimed versions names each root it
published under, `refs/timber/root` beside the version tags in the
shared history, so a move is read from git alone (22, 62). The first
publish after a move, before it builds or claims anything, marks the old
root with where it went, the tag `moved` in its own at bytes naming the
new root; copies there every version the record claims, with every
claim on its digests (103); makes each channel's name at its chain's
head, so the chain goes on from it (105); and records the new root last.
A carry that stops partway is carried again by the next publish, which
writes only what is missing. The old root then answers every read and
write of its own, its components' and its cache repositories with where
its history went, and an artifact's name there still reads as before;
a pool's push still writes its cache entries there, since they are no
history and serve the builds of the revisions they came from. Cache
entries are not carried: the pool's next run fills the new root.
A root left takes no history again: a publish whose store is bound for
it, another repository's at the old address, a checkout's whose remote
still names it, or a repository's moved back to it, is refused naming
where it went.

Each part of a repository's path is lowercased and escaped into one path
component the distribution protocol allows, `@acme/site` written
`0_40acme_2fsite`, and a path past 255 characters is refused naming it.
A registry that makes repositories only by a creation template, ECR
among them, refuses a put into one nobody made, and the refusal names
the repository in the registry's own words (see
[self-hosting](/timber/guides/self-hosting/)). An artifact is an OCI manifest whose artifact type names
the ecosystem, whose layers are the ecosystem's own bytes and whose
config is its own metadata, in exactly the bytes the layout writes, so
one artifact has one digest in both (1). An attestation is a DSSE
envelope holding an in-toto statement, attached as a referrer of the
digest it is about: a manifest typed by timber's envelope type, its one
layer the envelope, the statement's predicate type in its
`in-toto.io/predicate-type` annotation. claims-of lists the subject's
referrers of that type by the referrers API, or, where a registry has
none, by the referrers tag the distribution specification defines in its
place. A name is a tag, escaped into one where it holds a character a
tag cannot, `1.0.0+build.1` written `1.0.0_2bbuild.1` and read back as
written. No registry refuses a
tag put by the digest it is expected to be at, so name reads the tag
first and refuses a move from anywhere else as far as that read shows,
and reads it back after the put, again while the registry still answers
the former place, for up to 30 seconds: a tag found at another digest is
a lost race, refused naming that digest and never retried (70, 109). A
read can lag a put, as ECR's do, so nothing rests on the check: a
channel's name found elsewhere is repaired from the ledger (109). A tag names only a manifest, so a
cache entry's bytes are named through a cache manifest whose one layer
is the bytes, held in the cache repository, and resolve answers the
bytes' digest (100); a cache
manifest is no artifact, and claims-of never lists it. The credential is
the host's, from its Docker configuration and the credential helpers it
names, reached when the registry asks for one and kept nowhere (64). A
read asks the registry's token service for the scope its challenge
names, and a write for pulling and pushing its repository, whatever the
challenge names. Bytes a registry answers held and will not serve, as
GitHub's registry does in a package that holds no manifest yet, are
unreadable in the registry's words, never absent (59).

zot and the reference distribution are proven in the gate, each started
for the test. ECR needs a person's live AWS session, which the gate does
not hold, so its run is a check of its own outside the gate, run by hand
with `moon run ':#check-ecr'` against a repository the host names. ECR
was proven by that run's push on 2026-10-25, in us-west-2; ADR 0015
records what ECR answered. GitHub's registry needs a person's token as
well, so its run is the GHCR check, outside the gate beside ECR's, run
by hand with `moon run ':#check-ghcr'` against a repository the host
names. GitHub's registry was proven by three runs of it in a row on
2026-11-17; record 0039 records what GitHub's registry answered. It was
proven under a root per repository by one run on 2026-11-18, each
repository's components and cache in packages under its own
`<root>/<owner>/<name>/` and each artifact's name in a package under
`<root>/artifact/`, the index's claims read there by a store bound for
another repository; record 0041 records the run. It was proven carrying
a moved repository's history by one run on 2026-11-18, a version, its
claims and a channel carried from one root to another under the root it
names, the old root answering where its history went; record 0042
records the run.

The layout is bound for a host by its bindings file, `[store] layout =
"<path>"`, and a registry by `[store] registry = "<host>/<root>"`
(see [self-hosting](/timber/guides/self-hosting/)). A host with no
file, or a file with no `[store]`, binds the layout at
`~/.local/share/timber/layout`, under `$XDG_DATA_HOME` where it is
set, and names it in its record by that path in full (118, C.2). A
publish makes the layout, the given one with its parents, the first time
it asks the store anything, where the path is missing or an empty
directory, and writes into it thereafter, so a publish refused before it
asks the store makes none;
verify and status never make or write one, and answer a layout that is
not there unreadable naming its path; nothing makes a registry's
repository.

## Adding one

A store profile implements the one store interface and nothing of the
core, and is bound for a host by the operator (92). It passes the one
conformance suite, which holds it to Parts A and B; a profile that fails
the suite is not one (93).
